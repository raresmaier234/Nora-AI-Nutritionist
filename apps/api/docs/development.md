# Development

## First-time setup

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -e .
cp .env.example .env
```

Edit `.env` if your local PostgreSQL differs from the default in `.env.example`.

## Running the server

```bash
uvicorn app.main:app --reload
```

or, without the `uvicorn` CLI:

```bash
python -m app.main
```

(must be run as a module — `python app/main.py` breaks the `app.*` imports). This path reads
`APP_HOST` / `APP_PORT` / `DEBUG` from `.env`.

Swagger UI at http://127.0.0.1:8000/docs, ReDoc at http://127.0.0.1:8000/redoc, raw OpenAPI
spec at http://127.0.0.1:8000/openapi.json — all three are generated by FastAPI automatically,
no separate setup needed. See [api.md](api.md) for how to document a new endpoint.

## Sign-in (Supabase)

Every endpoint except `/api/v1/health` needs a Supabase access token (see
[architecture.md](architecture.md#authentication)). Locally, point the API at the
**development** Supabase project in `.env`:

```bash
# The project URL. Without it, every endpoint but health answers 503 "Sign-in is not
# configured on this server".
SUPABASE_URL=https://<project-ref>.supabase.co
# The project's secret API key (sb_secret_…). Only used by DELETE /api/v1/users/me; without
# it account deletion answers 503. Never put it in the app.
SUPABASE_SECRET_KEY=sb_secret_...
```

The same two variables are set per Railway environment, each to its own Supabase project
(`nora-development`, `nora-production`). The project must sign tokens with an **asymmetric**
JWT signing key (ES256, Supabase's recommendation); tokens signed with the legacy shared
secret (HS256) are always refused. The API fetches the public keys from Supabase on the first
request, so it needs internet access; no key has to be copied into `.env` for verification.

### Calling the API by hand

You need the access token of a signed-in session: sign in from the app against the
development project and take `session.access_token` (supabase-js:
`(await supabase.auth.getSession()).data.session?.access_token`). It is valid for about an
hour. Then:

```bash
curl -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8000/api/v1/users/me
```

or paste it into **Authorize** in Swagger (`/docs`). The first request with a new user's token
creates their `users` row.

Tests need none of this: they never call Supabase. `tests/auth_tokens.py` makes an ES256 key
pair and signs tokens with it, and `tests/conftest.py` points the API at that key. The
`client` fixture is signed in as a new user each test (`user_id`), `other_client` as a second
user, and `anon_client` sends no token.

### Admin scripts

Both act on the database `DATABASE_URL` points at, and look the user up by email (ignoring
case). The user must have signed in to the app once, which creates their row.

```bash
# Give the food log from before accounts to its owner: every entry without a user is
# assigned to this user. Run once per environment that has such entries, then see the
# NOT NULL follow-up in docs/database.md.
python scripts/claim_shared_log.py you@example.com

# Put a user on a plan by hand (no expiry), until payments exist.
python scripts/set_plan.py you@example.com premium
python scripts/set_plan.py you@example.com basic
```

Each refuses, changing nothing, an email no user has or one that more than one user has (the
error lists their ids).

## Food search (Elasticsearch)

Food search runs on Elasticsearch when it's configured, and on PostgreSQL otherwise — so this
is optional, but it's what gives typo tolerance, search as you type and English/Romanian
matching (see `GET /api/v1/foods` in [api.md](api.md)).

```bash
docker compose up -d elasticsearch                      # Elasticsearch 9.5, on 127.0.0.1:9200 only
echo 'ELASTICSEARCH_URL=http://127.0.0.1:9200' >> .env  # turn it on for the API and scripts
python scripts/index_foods.py                           # build the index from the foods table
```

Docker Desktop must be running. The container uses about 1.5 GB of memory; security is off
because it only listens on this machine.

Rebuild the index (`python scripts/index_foods.py` again — safe while the API is running) after
editing the synonyms in `app/services/food_synonyms.py` or the analyzers in
`app/services/food_index.py`. New foods from `scripts/ingest_foods.py run` are indexed as
they're saved.

## Running tests

```bash
pytest
```

`tests/test_food_search_index.py` needs Elasticsearch running (`docker compose up -d
elasticsearch`) and is skipped otherwise. It builds a throwaway index per test, so the
development index is never touched; every other test searches PostgreSQL.

## Migrations

```bash
# after adding/changing a model in app/db/models/
alembic revision --autogenerate -m "describe the change"

# review the generated file in alembic/versions/, then:
alembic upgrade head
```

## How to add a new route

1. Pick the existing route module it belongs to (`app/api/routes/foods.py`, etc.), or create a
   new one if it's a genuinely new resource.
2. Add the handler function with a `@router.get/post/...` decorator.
3. If it's a new file, register it in `app/api/router.py`.
4. Keep the handler focused on HTTP concerns — parse input (via a Pydantic schema), call a
   service or the DB, return a schema.

## How to add a new Pydantic schema

Add a class to `app/schemas/` (one file per resource is a reasonable default, e.g.
`app/schemas/food.py`). Schemas describe API request/response shapes — they are not database
models. A typical resource ends up with a couple of small classes, e.g. `FoodCreate` and
`FoodOut`.

## How to add a new SQLAlchemy model

1. Create `app/db/models/<name>.py`:

   ```python
   from sqlalchemy import String
   from sqlalchemy.orm import Mapped, mapped_column
   from app.db.database import Base

   class Food(Base):
       __tablename__ = "foods"

       id: Mapped[int] = mapped_column(primary_key=True)
       name: Mapped[str] = mapped_column(String, nullable=False)
   ```

2. Import it in `app/db/models/__init__.py` so Alembic can see it.
3. Generate and review a migration (see above).

## Where business logic goes

- If a route is a straightforward "validate input, one DB query, return it" — the logic stays
  in the route handler. Don't create a service just for the sake of layering.
- Once a route needs multiple steps, calls an external API/AI service, or that logic is shared
  by more than one route, move it into `app/services/<name>.py` and have the route call it.

## Coding conventions

- Type hints on function signatures.
- Keep files small and focused — one route group, one model, one service per file.
- No abstractions (base classes, generic repositories, factories) until a second concrete case
  actually needs them.
- Secrets and environment-specific values go through `app/core/config.py` / `.env`, never
  hardcoded.
